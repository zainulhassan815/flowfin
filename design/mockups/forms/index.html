Design · Forms

One form, five fillings

Today FlowFin has four add-forms and four layouts. Two field idioms — label-above and label-beside — are mixed, sometimes on the same screen; only Add-transaction has a keypad; placeholder text is dark enough to read as data already entered; and Save sits inert without saying what it wants. This page defines one anatomy and fills it five ways, including the Add-budget screen that doesn't exist yet.

What's wrong today

  1. Four layouts. Add-recurring alone uses label-above fields for Name and Frequency and label-beside rows for From, Category and Note.
  2. No keypad on recurring or debt. Their amount reads as a heading, not the form's primary input.
  3. Placeholders read as values. "Gym Membership" and "Monthly gym fees…" look filled in.
  4. Add-account is half empty — three fields, then 400px of nothing, and a plain Rs 0.00 text field.
  5. Save never says why it's off. Every form opens on a grey button with no hint of what's missing.
  6. Add-debt defaults to off-book — the toggle is off, so the rarer case is the default.

The rules

  • One field idiom. Every input is a form-row: mono label left at 84px, serif value right. A row that chooses (account, category, date, person) carries a chevron and opens a sheet. A row that types (name, note, reason) edits in place — it has to, or "opens on the name" would mean opening with a sheet already in your face.
  • Amount is always first and always live. Where it isn't the opening move it collapses to a tappable pill, never a dead readout.
  • A form opens on the field it is about. A money event — transaction, debt — opens on the amount, because the number is the point. A thing you are naming — account, budget, recurring — opens on the name. Nothing is configured per screen; it falls out of what the screen is.
  • The keypad follows focus. Focus the amount and it rises; touch any other field and it drops. One mechanism, and with four or five inputs per form of which exactly one is numeric, "is the amount focused?" is the whole state.
  • Keypad and Save are one pinned dock. The pad sits on top of the Save bar, content scrolls underneath, and Save never moves — so it can never fall below the fold again. When a text row has focus the system keyboard takes the pad's place in the dock; the two are never both up.
  • Placeholders are faint, italic, and prefixed e.g.
  • Optional fields are invitations — + Add a note, not an empty row taking up space.
  • A blocked Save names its blocker.

03 · What this changes in code

Reuses what exists

  • FlowFinFormRow becomes the only field. Its label column is already 84px and single-line.
  • The keypad, amount hero, chips, swatch grid and toggle card all exist in core/designsystem.
  • The budget's schedule reuses Recurrence, RecurringDraft and FireSchedule — no new period concept in the data model.

Genuinely new

  • Add-budget screen + route. CreateBudget already exists and is unreachable from the app.
  • A budget's funding schedule. A recurring Allocation — the one kind RecurringDraft can't express yet.
  • The dock — keypad and Save pinned together, pad bound to which field has focus. Initial focus is a property of the form (money event → amount, named thing → name), not a flag to set per screen.
  • The blocked-Save reason, new to the design system.
  • Once a budget has a monthly funding figure, the Accounts card can honestly read "Rs 22,000 of Rs 28,000 this month" instead of a lifetime total.
04 · Before we build

Blockers — code says no

  1. The database forbids a recurring allocation. Transactions.sq carries CHECK ((kind IN ('INCOME','EXPENSE')) OR recurring_id IS NULL). A budget's funding schedule is a recurring allocation, so this CHECK has to widen — and in SQLite that means a table rebuild, i.e. a real migration or a deliberate pre-launch wipe. There are no .sqm files yet, so this is the first one.
  2. A schedule's direction is inferred, and an allocation breaks the inference. RecurringRepositoryImpl.fire() reads income = toAccountId != null; an allocation sets both accounts, so it would be filed as INCOME with both sides populated and no category — which the per-kind CHECK rejects at insert. Same trap in RecurringSchedule.isExpense. Either add an explicit kind, or make "both set = allocation" an written rule in the model.
  3. Nothing can be edited. There is no edit route in FlowFinRoutes and nothing calls TransactionRepository.updateContent — it is unreachable, exactly like CreateBudget. Decide now whether these five forms double as edit forms; retrofitting an edit mode into a form built only to create is the expensive way round.

Not drawn yet

  • Ad-hoc allocation. "Move Rs 5,000 into Food, now" has no screen today and none here. A funding schedule doesn't remove the need — it's the top-up you do when the envelope runs dry mid-month.
  • Record a payment against a debt — an existing form with its own mockup, not folded into this anatomy.
  • Category add / edit — a bottom-sheet form with the icon and colour grids. Add-budget needs those same grids, so the two should be settled together.
  • Transfer and Income variants of add-transaction. The tabs are drawn; their field sets differ (Transfer has From and To, no category) and aren't.
  • Add-budget has no icon or colour picker, while add-account does — budgets are identified by their tint everywhere else in the app.

New to the design system

  • The dock — pad + Save pinned as one unit, occupant bound to focus.
  • Blocked Save with its reason line. Needs a precedence rule when more than one field is missing — first empty in reading order is the honest answer.
  • FlowFinFormRow sub-line — used three times here ("Next: 22 Sep 2026", "The real account it draws from"). The component has label / value / valueDetail / aux and no second line.
  • The ＋ Add a note invitation row.

Already built — reuse, don't rebuild

  • FlowFinCalculatorPad, FlowFinHeroAmount, FlowFinTextField, FlowFinSwitch, FlowFinSegmentedControl, FlowFinTileIcon, FlowFinScopeTabs, FlowFinFormRow.
  • FlowFinScreenScaffold already owns IME insets, which is what makes the dock's keyboard swap cheap.
  • CreateBudget exists and is fully tested — the Add-budget screen is UI and routing, not domain work.
